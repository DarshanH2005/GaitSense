## Objective

Build a two-foot wearable prototype that:

- Samples four force-sensing resistors (FSRs) and one six-axis IMU per foot.
- Streams telemetry from each foot independently to an Android phone over BLE.
- Displays real pressure-channel readings and gait metrics without invented fallback values.
- Records labeled sessions for a reproducible ML workflow.
- Runs a small trained classifier on the phone and shows model availability/confidence honestly.
- Saves daily summaries, presents actual history, and exports actual recordings/reports.
- Provides firmware, assembly instructions, validation results, and documentation suitable for a final-year demonstration.

This is a research prototype for gait-pattern observation/classification. Disease diagnosis, Parkinson's screening accuracy, fall-risk prediction, clinical-grade pressure mapping, and all-day battery life are not established capabilities.

## User decisions and preferences

- Cost matters, primarily ESP32 and FSR prices. Cables are inexpensive locally.
- No custom PCB. Use breakout boards, soldered wires, optionally perfboard, and shoe-mounted enclosures.
- Latest working hardware assumption: **two generic ESP32-C3 SuperMini boards**, rather than the earlier XIAO ESP32-S3 proposal.
- Retain ADS1115 and four FSRs per foot. Reducing to three FSRs was discussed, not accepted as the build configuration.
- User will manage battery charging externally; do not keep insisting on onboard charging.
- A **7Semi TPS61023 fixed 5 V boost board per foot** was accepted as a viable power route. It feeds the SuperMini 5V pin, not 3V3.
- The original battery proposal was protected 3.7 V 500–600 mAh per foot. 300–400 mAh was discussed, but no final reduced capacity was confirmed.
- Phone-based ML was the proposed architecture when switching to the C3. Do not represent it as an already trained or integrated capability.
- User asked whether hardware makes the project “100% possible.” Response: it is capable of the planned prototype, but accuracy, power stability, RF reliability and real performance require tests.
- Prefer concrete progress over repeated confirmation. No need to redesign the project merely because a cheaper alternative exists.
